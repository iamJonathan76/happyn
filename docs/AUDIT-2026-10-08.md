# Audit avant lancement — 2026-10-08

Question posée : « le chantier est-il sûr ? ». Réponse construite sur des
vérifications exécutées, pas sur une relecture : chaque constat ci-dessous dit
comment il a été établi.

**Méthode.** Analyseurs Supabase (`supabase db advisors`, sécurité et
performance) sur la base de PRODUCTION, chaque alerte revérifiée à la main ;
vérification de types stricte (`tsc --strict`) des 12 fonctions Edge ; recherche
de secrets dans les fichiers suivis et dans tout l'historique git ;
`flutter analyze` et `flutter test` ; lecture des fonctions sensibles telles
qu'elles tournent en production (pas telles que le dépôt les décrit).

## 1. Architecture

```
App Flutter (iOS · Android)          Site (Netlify, statique)
   │  clé publique, dans le binaire        │
   ▼                                       ▼
Supabase ─ Auth (courriel, Google)
         ─ API REST ── RLS ── Postgres (26 tables, 67 fonctions serveur, déclencheurs)
         ─ Storage (3 buckets)
         ─ Realtime (messages privés)
         ─ 12 fonctions Edge ── seules à connaître les secrets
                │
                ├── Stripe (paiements, Connect, webhook signé)
                ├── Firebase (push, via send-push)
                ├── Resend (courriels, via notify-report)
Photon (adresses) · Sentry (erreurs) · Google Sign-In : appelés depuis l'app
```

**Ce qui est propre**
- Le contrôle d'accès vit en base, jamais dans l'app : la clé de l'app est
  publique par conception. C'est appliqué partout — sauf dans le cas trouvé au
  § 2.1, qui était précisément une exception à cette règle.
- Les secrets (Stripe, Firebase, HMAC des billets, service_role) ne quittent
  jamais Supabase. Recherche dans tout l'historique git : aucune clé secrète,
  seulement des exemples dans la documentation (`whsec_...`).
- L'argent a une seule définition : `event_ledger()`. Le montant d'un paiement
  est calculé par le serveur à partir du prix en base, jamais envoyé par l'app.
- Les 12 fonctions Edge passent `tsc --strict`.

**Ce qui est désordonné**
- **64 migrations appliquées à la main**, et l'historique de la CLI est vide :
  un `supabase db push` les rejouerait toutes. Chaque modification a été
  comparée octet pour octet à la production avant d'être réécrite — discipline
  qui tient, mais qui ne doit pas dépendre de la mémoire de quelqu'un.
- **Trois gros écrans** : création d'événement (1 420 lignes), fiche
  d'événement (988), profil (950). Lisibles, mais chaque modification y coûte
  plus cher.
- **Textes légaux en trois copies** (base, app, site).
- **Notifications** : la base les rédige (en anglais, puis traduites par un
  déclencheur). Simple et sûr ; la version qui suit la langue après coup est
  notée comme reportée.

## 2. Sécurité

### 2.1 CRITIQUE — des billets payants sans payer (corrigé, à appliquer)

`issue_tickets` émet des billets sans paiement, pour les événements gratuits.
Elle ne vérifiait jamais le prix : seul l'écran faisait le tri. N'importe quel
compte pouvait appeler `/rest/v1/rpc/issue_tickets` avec l'identifiant d'un
palier payant et recevoir des billets valides, QR signé compris. Elle ne
vérifiait pas non plus qu'un événement privé avait été déverrouillé.

Établi en lisant la fonction de production ; le correctif est exécuté sur
Postgres jetable (palier payant refusé, gratuit accepté, privé refusé sans le
code, accepté après). Pas testé en production : ça créerait un faux billet.
→ `supabase/migrations/20261008000000_security_hardening.sql`.

### 2.2 Corrigé dans la même migration

- **Code d'invitation essayable sans compte** : `unlock_private_event` était
  appelable par `anon`. Fermé (comptes connectés seulement). La limitation de
  débit reste à faire (§ 2.4).
- **7 fonctions sans `search_path` figé**, dont une `SECURITY DEFINER`
  (`handle_new_user`, à chaque inscription). Figé.
- **Annuaire des membres lisible sans compte** : `public_profiles` et
  `feed_posts` étaient ouverts à `anon`. Fermés ; ni l'app avant connexion ni
  le site ne les lisent.

### 2.3 Déjà sain (vérifié)

- Toutes les tables publiques ont la RLS (aucune alerte « RLS désactivée »).
  `payments` et `admin_actions` n'ont aucune politique : c'est voulu, seul le
  serveur y écrit et y lit.
- Les fonctions sans connexion se protègent elles-mêmes : signature HMAC du
  webhook Stripe ; secret partagé comparé en temps constant pour push,
  signalements et versements ; la validation d'un billet vérifie que c'est
  l'organisateur qui scanne.
- Billets : aucune politique d'écriture sur `tickets` ; QR signé rotatif.
- Annulation : un événement ne passe plus en « annulé » sans rembourser
  (garde du 2026-10-07).

### 2.4 Reste ouvert

| Point | Gravité | Quand |
|---|---|---|
| Aucune limitation de débit (code d'invitation, recherche, envois) | moyenne | avant d'ouvrir à des inconnus |
| Nonce désactivé sur la connexion Google | moyenne | avant d'ouvrir les inscriptions (`LANCEMENT` § 3.2) |
| Buckets publics : qui a l'URL d'une photo privée la voit | faible, assumé | avant un premier événement privé d'un tiers |
| Protection contre les mots de passe compromis (HaveIBeenPwned) désactivée | faible | réglage du tableau de bord Supabase |
| ~~Aucun test automatique des règles d'accès~~ | fait | `tests/rls/run.sh`, 64 règles — voir § 7 |

## 3. Cas limites

**Tenu** : paiement refusé ou abandonné (le billet n'existe qu'après le
webhook) ; webhook rejoué (émission idempotente) ; paiement lent (écran
d'attente qui interroge) ; annulation pendant un versement (refusée) ;
remboursement d'un billet transféré (refusé, décidé) ; suppression de compte
avec de l'argent en jeu (refusée) ; erreurs serveur affichées au lieu d'écrans
vides (les `catch` silencieux ont été retirés, sauf deux justifiés).

**Non vérifié** : comportement sans réseau ou sur réseau lent ; app fermée en
plein paiement ; Stripe ou Resend en panne.

## 4. Base de données

Structure normalisée, argent en cents, une ligne de registre par paiement,
adresses privées dans leur propre table. Les analyseurs signalent, sans effet à
l'échelle actuelle :

- **43 politiques** qui recalculent `auth.uid()` à chaque ligne : écrire
  `(select auth.uid())` les rend constantes. Premier levier de performance.
- **23 clés étrangères sans index.**
- **11 doublons de politiques** (ex. deux politiques de lecture identiques sur
  `profiles`) et **1 index en double** sur `categories` : du désordre hérité,
  sans risque, à nettoyer.

## 5. Tests en conditions réelles

- **Fait** : iPhone et Android réels, très grande police.
- **Pas fait** : petit écran (iPhone SE), réseau lent, refus des permissions
  (caméra, notifications, position), mode avion.
- **Tests automatiques** : 38, tous de logique pure (âge, dates, prix,
  identifiants). Zéro test d'écran. **Zéro test des règles d'accès** — or les
  quatre vraies failles du projet (publications, catégories de billets, adresse
  exacte, et aujourd'hui `issue_tickets`) étaient toutes de cette famille.
  Postgres est maintenant installé sur le Mac : c'est le chantier qui rapporte
  le plus.

## 7. Mise à jour du même jour : les tests des règles d'accès

`tests/rls/run.sh` rejoue le schéma réel de la production sur un Postgres
jetable et vérifie 64 règles (visiteur, compte ordinaire, organisateur,
suspendu, bloqué, modérateur, serveur). Premier passage : **61 / 64**. Les trois
échecs étaient deux vraies failles, absentes de l'audit à la main :

- **Un compte suspendu pouvait se rétablir lui-même** en effaçant
  `suspended_at` de son propre profil. La suspension ne tenait que tant que la
  personne l'ignorait.
- **Les brouillons étaient lisibles par tout le monde**, visiteurs compris :
  « dépublier » ne retirait l'événement que de l'écran, pas de l'API.

Corrigé par `20261008010000_access_rule_fixes.sql` : 64 / 64.
